## Symptoms
`kubectl get pods -n prod` shows `CrashLoopBackOff` with a rising RESTARTS
count, or `Reason: OOMKilled` / `Exit Code: 137` under Last State. Callers see
`connection refused`, `upstream connect error or disconnect/reset before
headers`, or 503 `no healthy upstream` when no ready endpoints remain. If only
some replicas crash, the error rate is partial.

## Diagnosis
1. `kubectl describe pod <pod> -n prod` and read Last State, Reason, and Exit
   Code. 137 = killed for memory (OOMKilled); 1 or 2 = application error.
2. `kubectl logs <pod> -n prod --previous` for the crash output, for example
   `KeyError: 'PAYMENTS_API_URL'` or `failed to parse config`.
3. Timing matters: OOMKilled within the first minute after start means the
   memory limit is too low for startup (or a config change raised usage). A pod
   that runs for hours and is OOMKilled after steady growth is a leak; see
   RB-APP-001.
4. Check what changed: `kubectl rollout history`, ConfigMap or Secret edits.

## Mitigation
- Application error after a deploy or config change: revert it (RB-DEPLOY-001,
  or `kubectl rollout undo` after restoring the ConfigMap).
- OOMKilled at startup: raise `resources.limits.memory` (for example 256Mi to
  512Mi) and keep requests equal to limits for memory.
- Do not delete pods in a loop; it hides the restart count you need.
